Scope note for the report writer: everything below was fetched between 29 and 30 September 2026 unless it is marked as coming from the State of AI in Design Systems corpus, which is a snapshot of 26–28 July 2026 (one record, Coinbase CDS, was researched on 9 September 2026). ## Key question 1: Declarative generative-UI formats and their catalog models

### Takeaway
There are now two families. Schema-constrained declarative formats (A2UI, json-render, OpenUI Lang, Open-JSON-UI) make the agent emit a data structure that can only name components from a catalog the client declares, and A2UI is the only one with a published catalog negotiation, catalog versioning rules and a standard validation-error message that feeds back to the agent. Tool-to-component bindings (CopilotKit `useComponent` / `useRenderTool`, Tambo, AI SDK typed tool parts) are React-first and treat the registered tool or component set as the catalog, while MCP Apps is open-ended HTML in a sandboxed iframe with no catalog at all.

### Cited Findings

#### A2UI (Google)
- Current version: v0.9.1 is described as production-ready; v1.0 is a candidate that adds client-to-server RPC (`actionResponse`) and renames `theme` to `surfaceProperties`; v0.9 and v0.8 remain available as legacy. — [a2ui.org](https://a2ui.org/)
- A2UI positions the catalog as a security boundary: "Agents can only use pre-approved components from your catalog—no UI injection attacks." The home page also links an A2UI Composer at a2ui-composer.ag-ui.com. — [a2ui.org](https://a2ui.org/)
- v0.9.1 server-to-client messages are `createSurface` (carries `surfaceId` and `catalogId`), `updateComponents`, `updateDataModel` and `deleteSurface`; "A surface must be created before any `updateComponents` or `updateDataModel` messages can be sent to it." Client-to-server messages are `action` and `error`. — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Components are a flat adjacency list: "The tree structure is built implicitly using ID references." Each component has an `id`, a `component` type name and its properties. — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Data binding uses JSON Pointer (RFC 6901): absolute paths start with `/`; relative paths resolve inside template scopes for collections. `updateDataModel` "replaces the value at the specified `path` with the new content." — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Streaming: messages are JSONL, each with a `version` field and exactly one message-type key. — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Validation and repair: the spec defines a standard client error with `code: "VALIDATION_FAILED"`, `surfaceId`, a JSON Pointer `path` and a `message`, which lets the agent self-correct generated UI. — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Transport bindings listed in the spec: A2A, AG-UI ("low latency and shared state message passing between front ends and agentic backends"), MCP, SSE, WebSockets and REST. — [A2UI v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/)
- Catalog format: "a JSON Schema file that defines the UI components, functions, and themes an agent can use." Top-level properties are `catalogId`, `components` (JSON Schema per component), `functions` and `theme`. All agent A2UI JSON is validated against the chosen catalog. — [A2UI Catalogs concept](https://a2ui.org/concepts/catalogs/)
- `catalogId` is conventionally a URI, but "This URI does not imply that the agent or client downloads the catalog at runtime. The catalog definition must be known to the agent and client beforehand (at compile/deploy time)." Catalogs should carry `$id` and `catalogId` set to the same URI. — [A2UI Catalogs concept](https://a2ui.org/concepts/catalogs/)
- Client registration: the client sends `a2uiClientCapabilities.supportedCatalogIds` in every message's metadata, "ordered by preference"; the agent may advertise its own `supportedCatalogIds` in its A2A AgentCard; at `createSurface` the agent "selects the best match from the client's `supportedCatalogIds` list. This choice is locked for the lifetime of that surface." Inline catalogs sent at runtime are "supported but not recommended in production." — [A2UI Catalogs concept](https://a2ui.org/concepts/catalogs/)
- Catalog versioning rules: additive only; "Never delete existing components, functions, or properties. Mark them `deprecated: true` along with an `x-deprecated-reason` instead"; type invariance; open enums (renderers "handle unknown enum variants"); graceful fallback for unknown components; breaking changes go in a new versioned `catalogId` URI (for example `.../v2/catalog.json`), and clients can support both during migration. — [A2UI Catalogs concept](https://a2ui.org/concepts/catalogs/)
- Design system guidance, verbatim: for mature frontends, "Define a catalog that mirrors your existing design system"; the custom-catalog guide says to "build catalogs that directly reflect your client's design system rather than trying to map a generic catalog (like the Basic Catalog) to it through an adapter." The same guide says "Detailed guides for each framework coming soon." — [A2UI Catalogs concept](https://a2ui.org/concepts/catalogs/); [Defining your own catalog](https://a2ui.org/guides/defining-your-own-catalog/)
- A2UI v0.9 (Google Developers Blog, 17 April 2026) renamed the optional "Standard" component set to "Basic" because "Frontend developers don't want new components. They already have a design system." It lists React, Lit, Angular and Flutter as supported renderers, says transports can be "MCP, Websockets, REST, AG UI, A2A, or whatever you want," adds client-defined functions for validation and client-to-server data syncing, and names AG2, Vercel's json-render, Oracle Agent Spec and CopilotKit as ecosystem participants. — [A2UI v0.9 announcement](https://developers.googleblog.com/a2ui-v0-9-generative-ui/)

#### A2UI carried over AG-UI
- AG2's `A2UIAgent` with `AGUIStream` uses an event interceptor that splits text from A2UI JSON and emits the A2UI operations as an AG-UI `ActivitySnapshotEvent` with `activityType: "a2ui-surface"`, which `@copilotkit/a2ui-renderer` consumes. The agent supports "optional schema validation with automatic retry." Page dated 2026-06-26. — [AG2 docs: A2UI over AG-UI](https://docs.ag2.ai/latest/docs/user-guide/ag-ui/a2ui)
- CopilotKit runtime enables A2UI with `a2ui: {}` on `CopilotRuntime` (optionally scoped, for example `a2ui: { agents: ["my-agent"] }`), and the React provider takes `<CopilotKit runtimeUrl="/api/copilotkit" a2ui={{ theme: myCustomTheme }}>`. — [CopilotKit docs: A2UI](https://docs.copilotkit.ai/generative-ui/a2ui)
- CopilotKit's custom-catalog API is `createCatalog(definitions, renderers, { includeBasicCatalog: true })`: "Definitions are platform-agnostic (Zod schemas + descriptions). Renderers are platform-specific (React components). TypeScript enforces that renderer keys match definition keys exactly." `extractSchema(definitions)` produces the JSON-serializable view for the runtime's `a2ui.schema` config, and the catalog is passed as `a2ui={{ theme, catalog }}`. — [@copilotkit/a2ui-renderer 1.61.2 SKILL.md](https://cdn.jsdelivr.net/npm/@copilotkit/a2ui-renderer@1.61.2/skills/a2ui-renderer/SKILL.md)
- In Angular with CopilotKit, `provideA2uiCatalog(catalog)` registers the catalog and `connectAgentContext` serializes it as an AG-UI context entry (`catalogToContextEntry`, marker description "A2UI Custom Catalog"); server-side `addCustomCatalogInstructions` weaves the `catalogId` and component descriptions into the system prompt. Setting `sendCatalogDescription: false` sends only the catalog ID, to limit prompt-injection risk, with schemas coming from a trusted server registry. Schemas are converted with `zodToJsonSchema({ $refStrategy: 'none' })`. Author Manfred Steyer, 1 May 2026 (third-party, not Google or CopilotKit). — [Angular Architects: Custom Catalogs in A2UI](https://www.angulararchitects.io/en/blog/custom-catalogs-in-a2ui-your-own-components-for-ai-generated-uis/)
- CopilotKit's VS Code extension has an "A2UI Catalog" sidebar that discovers catalog files importing `@copilotkit/a2ui-renderer` and previews each component "with fixture-driven scenarios and hot-reload on save"; fixtures are JSON or TypeScript files next to components, each top-level key a named scenario, validated on save. It also ships an "AG-UI Inspector" that connects to `{runtimeUrl}/cpk-debug-events` and shows every event in a "filterable, color-coded stream." — [CopilotKit docs: VS Code extension](https://docs.copilotkit.ai/angular/vs-code-extension)

#### json-render (Vercel Labs)
- Catalog declared with `defineCatalog(schema, { components, actions })` from `@json-render/core`; each component entry has `props` (a Zod object), `slots` (for example `["default"]`) and an optional `description`; actions have Zod `params`. `catalog.prompt()` (or `catalog.prompt({ customRules: [...] })`) generates the system prompt. — [json-render docs: catalog](https://json-render.dev/docs/catalog)
- Output is a spec with `root` and `elements`; data binding uses `$bindState`, `$state`, `$item` and `$index`. — [json-render.dev](https://json-render.dev/)
- Streaming: "Each JSONL patch adds to the spec and the UI updates in real time"; the README names `createSpecStreamCompiler` with `compiler.push(chunk)`. — [json-render docs](https://json-render.dev/docs); [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render)
- Not React-only: 29+ packages including `@json-render/react`, `vue`, `svelte`, `solid`, `react-native`, `next`, `remotion`, plus React PDF, React Email, Ink, Three.js and image renderers, and `@json-render/shadcn` with "36 pre-built shadcn/ui components." Apache-2.0, about 18.4k stars at fetch time. The home page also mentions export to standalone React code. — [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render); [json-render.dev](https://json-render.dev/)

#### MCP Apps and MCP-UI
- MCP Apps is an extension to the core MCP spec. A tool declares `_meta.ui.resourceUri` pointing to a `ui://` resource containing HTML; hosts can preload it before the tool is called, "enabling features like streaming tool inputs to the app." The resource renders in a sandboxed iframe; `_meta.ui.csp` and `permissions` control external origins and capabilities; app and host talk JSON-RPC over `postMessage` with mostly `ui/`-prefixed methods (for example `ui/initialize`). — [modelcontextprotocol.io: MCP Apps](https://modelcontextprotocol.io/docs/extensions/apps)
- The spec file is dated 2026-01-26; the `App` class from `@modelcontextprotocol/ext-apps` is optional; starter templates exist for React, Vue, Svelte, Preact, Solid and vanilla JS. Supported hosts listed: Claude, Claude Desktop, VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman, MCPJam and Archestra.AI. Hosts can build on `@mcp-ui/client` or the SDK's AppBridge. — [modelcontextprotocol.io: MCP Apps](https://modelcontextprotocol.io/docs/extensions/apps)
- MCP-UI says it has been "standardized into MCP Apps" and now serves as "a community playground for future enhancements"; packages are `@mcp-ui/client` (`AppRenderer`) and `@mcp-ui/server` (`createUIResource`). — [mcpui.dev](https://mcpui.dev/)
- AG-UI describes MCP-UI as a Microsoft + Shopify "fully open, iframe-based Generative UI standard extending MCP." — [AG-UI: Generative UI specs](https://docs.ag-ui.com/concepts/generative-ui-specs)
- Older (August 2025): Shopify's MCP-UI write-up lists three delivery methods (inline HTML via `srcDoc`, remote resources in an iframe, and Remote DOM), says Remote DOM lets the host render with its own component library, and says "Components don't directly modify state—they bubble up intents that the agent interprets" (`view_details`, `checkout`, `notify`, `ui-size-change`). — [Shopify Engineering: MCP UI](https://shopify.engineering/mcp-ui-breaking-the-text-wall)
- Corpus (July 2026): Storybook's `preview-stories` tool in `@storybook/addon-mcp` renders story previews inline via MCP Apps. — [Storybook docs: MCP](https://storybook.js.org/docs/ai/mcp)

#### Open-JSON-UI
- AG-UI describes it as an "open standardization of OpenAI's internal declarative Generative UI schema." — [AG-UI: Generative UI specs](https://docs.ag-ui.com/concepts/generative-ui-specs)
- CopilotKit's generative-ui repo groups it with A2UI as "Declarative Generative UI" and links CopilotKit docs for it, not an OpenAI-hosted spec. — [github.com/CopilotKit/generative-ui](https://github.com/CopilotKit/generative-ui)

#### CopilotKit generative UI
- CopilotKit's taxonomy: Controlled generative UI (developer pre-builds components, agent picks and fills them, over AG-UI), Declarative (A2UI and Open-JSON-UI), Open-ended (MCP Apps). AG-UI is "the bidirectional runtime interaction layer beneath these patterns." — [github.com/CopilotKit/generative-ui](https://github.com/CopilotKit/generative-ui)
- React v2 hooks in the current reference: `useAgent`, `useAgentContext`, `useCapabilities`, `useComponent`, `useConfigureSuggestions`, `useCopilotChatConfiguration`, `useCopilotKit`, `useDefaultRenderTool`, `useFrontendTool`, `useFrontendTools`, `useHumanInTheLoop`, `useInterrupt`, `useRenderTool`, `useRenderToolCall`, `useSuggestions`, `useThreads`. `useCopilotAction` and `useCoAgentStateRender` do not appear in the v2 list. — [CopilotKit reference](https://docs.copilotkit.ai/reference)
- `useComponent`: "Register React components that your agent can render in the chat for Built-in Agent." — [CopilotKit docs: generative UI](https://docs.copilotkit.ai/generative-ui)

#### AG-UI's position and its own draft
- "AG-UI is not a generative UI specification — it's a User Interaction protocol that provides the bi-directional runtime connection between the agent and the application," and it "natively supports all of the above generative UI specs and allows developers to define their own custom generative UI standards as well." — [AG-UI: Generative UI specs](https://docs.ag-ui.com/concepts/generative-ui-specs)
- An AG-UI draft (author Markus Ecker) proposes a `generateUserInterface` tool whose arguments are `description`, `data` and an `output` JSON Schema; a secondary generator produces the UI, and user input is validated against the output schema before it returns to the agent. It names JSON Forms and React Hook Form as possible generators and notes provider limits (OpenAI's 1024-character tool description limit, uneven JSON Schema support for `$ref`, `oneOf`, nesting). — [AG-UI draft: Generative User Interfaces](https://docs.ag-ui.com/drafts/generative-ui.md)

#### Thesys C1 / OpenUI
- `docs.thesys.dev` now returns a 307 redirect to `https://www.openui.com/docs?from=c1`, so the C1 docs have been folded into OpenUI. — [docs.thesys.dev redirect, fetched](https://docs.thesys.dev/)
- OpenUI calls itself "A Generative UI toolkit for creating agents that respond with live, interactive interfaces instead of only text," says interfaces stay "consistent with your product and design system," and offers OpenUI Lang ("up to 67% fewer tokens than JSON") or JSON output, plus Autofix to "fix model output that would break your UI." — [openui.com docs](https://www.openui.com/docs?from=c1&utm_source=docs.thesys.dev&utm_medium=redirect)
- OpenUI Lang is "compact, line-oriented syntax" (`identifier = Expression`, for example `root = Stack([chart])`) that is "trivial to parse and render progressively"; the runtime "validates output and drops invalid portions, rendering only what's valid"; the backend "appends the generated component library prompt alongside your system prompt." The full grammar is at a v0.5 language specification page. — [OpenUI Lang](https://www.openui.com/docs/openui-lang)

#### Tambo
- Components register as `TamboComponent` objects with `name`, `description`, `propsSchema` (Zod) and `component`, passed to `TamboProvider` (`components`, `tools`, `apiKey`, optional `userToken`). Interactable components persist and update by ID through `withTamboInteractable()`. Props stream progressively; MCP is supported; self-hosted backend or Tambo Cloud; React only. — [docs.tambo.co](https://docs.tambo.co/)
- Tambo 1.0 shipped 10 February 2026 as "a fullstack, open-source generative UI toolkit for React"; the post names "Anthropic's MCP Apps, Google's A2UI, Vercel's json-render" as converging specs and stresses rendering "something meaningful while half the props are missing." — [Tambo blog: Introducing Tambo 1.0](https://tambo.co/blog/posts/introducing-tambo-generative-ui)

#### Vercel AI SDK
- "Generative UI is the process of connecting the results of a tool call to a React component." In AI SDK 5.0, tool parts use typed names `tool-${toolName}`, with states including `input-available`, `output-available` and `output-error`, rendered from `useChat` message parts. — [AI SDK: Generative User Interfaces](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)
- "AI SDK RSC is currently experimental. We recommend using AI SDK UI for production." (This covers `streamUI`.) — [AI SDK RSC overview](https://ai-sdk.dev/docs/ai-sdk-rsc/overview)

### Inferences
- A2UI is the only format here that treats the catalog as a versioned API with a negotiation step and a machine-readable error path back to the agent. That maps closely onto how a design system already versions a package, which makes it the strongest candidate for the contract layer of an AG-UI prototyping environment.
- A2UI's `catalogId`-known-at-deploy-time rule plus CopilotKit's "definitions vs renderers" split means a design system team could publish the catalog (definitions) once and let each platform (React, Angular, Lit web components, Flutter) supply renderers bound to its real components. None of the code-generating tools in key question 2 offers that multi-platform path.
- A2UI's `theme` (renamed `surfaceProperties` in the v1.0 candidate) is a per-catalog JSON Schema, not a token system. Binding it to DTCG tokens or CSS custom properties is left to the renderer.
- MCP Apps solves distribution and sandboxing, not design-system conformance: an MCP App can render anything, so it is the wrong layer for "only approved components," though it is a reasonable way to preview a design system's real components inside a chat host (as Storybook's `preview-stories` does).

### Gaps
- Open-JSON-UI: no OpenAI-hosted spec, repo or changelog was found; the only descriptions come from AG-UI and CopilotKit pages. Its catalog mechanism, validation and streaming model could not be established.
- A2UI launch date: a search listing shows Google's "Introducing A2UI" post dated 15 December 2025, but that page was not fetched.
- json-render: the exact validation API (for example a `validateSpec` function) and repair behavior on invalid output were not documented on the pages fetched.
- OpenUI: package names, the component-definition API and whether it is React-only were not on the pages fetched. The OpenUI Product Hunt launch (11 March 2026) and C1's April 2025 launch came from search listings only.
- CopilotKit: whether `useCopilotAction` and `useCoAgentStateRender` are formally deprecated in v2 was not confirmed; they are only absent from the v2 reference list.
- AI SDK: whether `input-streaming` is a named tool-part state and which non-React UI packages exist were not confirmed on the fetched page.
- A2UI renderers: whether the React renderer is first-party Google or community was not settled (the v0.9 post lists React among supported renderers).

## Key question 2: Design systems prototyping environments

### Takeaway
Every prototyping environment that design system teams actually use or describe generates code (usually React) against the real package plus prose guidelines, then checks adherence after the fact with linters, MCP validation tools or prompts; none of them constrains the model with a declarative catalog format. The most concrete first-party lessons come from Atlassian (templates and structured configuration beat open prompting; about 70% design-system accuracy in one pass; hallucinated imports, tokens and icons), Coinbase (a skill-driven eval at 100% vs 75.0% without it), Uber (Base MCP at 500+ users) and Supernova/Lovable/Bolt/v0 (versioned design-system contexts), while Figma Make kits have no named enterprise case study.

### Cited Findings

#### Figma Make kits
- Make kits (announced 2 April 2026) "combine design system components with detailed guidelines" and support code components via npm (public or "Figma's secure private registry") plus Figma library styles and tokens; claimed benefit: "Less cleanup before review and a shorter distance between what's prototyped and what ships." No customers are named. — [Figma blog: Make kits and Make attachments](https://www.figma.com/blog/introducing-make-kits-and-make-attachments/)
- Package requirements: Vite-compatible, published to npm or the org's Figma-hosted private registry, private scopes must not collide with public ones, public dependencies are auto-installed, and "Your package will be living in an environment that doesn't have access to the larger ecosystem of your codebase." Guidelines are authored in Make, not in the package. — [Figma Help: bring your design system package](https://help.figma.com/hc/articles/43602872461079)
- Corpus (July 2026): a Make kit is a React 18 npm package plus a `guidelines/` tree Make must read first, with Figma advising "Multiple short guidelines files are better than a few large files" and imperative rules; Make requires a Full seat on a paid plan; "No public case study found for Figma Make kits at a named enterprise design system." — [Figma: write design system guidelines](https://developers.figma.com/docs/code/write-design-system-guidelines/)
- Round trip back to Figma is a one-way snapshot: copied layers "aren't connected to the Figma Make file," "aren't interactive," and are "not automatically tied to your design system." — [Figma Help: Copy a Make preview as design layers](https://help.figma.com/hc/en-us/articles/35060759685015-Copy-a-Figma-Make-preview-as-design-layers)
- Corpus: Figma's MCP server also has `generate_figma_design` (live UI to Figma layers). — [Figma MCP tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)
- Corpus: zeroheight's remote MCP access modes also govern partner connectors "like Figma Make," and zeroheight documents "AI-accelerated prototyping in Figma Make" as one of three target workflows. — [zeroheight: remote MCP](https://help.zeroheight.com/hc/en-us/articles/43780251357979-Using-the-remote-zeroheight-MCP-server); [zeroheight MCP overview](https://help.zeroheight.com/hc/en-us/articles/48004395674011-zeroheight-MCP-overview)

#### Atlassian (ADS)
- Older (26 November 2025): Atlassian's internal AI prototyping setup combined about 2,000 lines of design-system instructions, "Fast" and "Full" templates with preconfigured code, JSON configuration files for deterministic changes (logo, navigation), the `@atlaskit/ads-mcp` server, an `offerings.json` content schema and an `llms.txt` manifest. From a screenshot it reached "70% Atlassian Design System accuracy in one pass." Early failures: "Incorrect component imports, wrong token names, icons that seem on-brand but don't exist." Lessons: "Structured configuration beats open-ended prompting; the more constraints...the more reliable the outputs became," and production code "at scale remains challenging." — [Atlassian: Turning handoffs into handshakes](https://www.atlassian.com/blog/design/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)
- The same fetch reported "85% of AI Builders Week participants reported more confident using AI tools," while a search listing of the same URL reads "Roughly 85% of designers and product managers at Atlassian are actively using AI prototyping tools." The two phrasings conflict; treat the 85% figure as unconfirmed. — [Atlassian: Turning handoffs into handshakes](https://www.atlassian.com/blog/design/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)
- AI Builders Week (10 March 2026) used Cursor, Figma Make, Replit, Rovo Dev, Rovo Studio and Solution Builder; "Moving closer to production code isn't without its challenges." — [Atlassian: A design technologist's take on AI builders](https://www.atlassian.com/blog/design/a-design-technologists-take-on-ai-builders)
- DESIGN.md eval (15 June 2026), login-screen task: no context 4.20M tokens / 43 turns; ADS MCP 3.75M / 35.1; ADS skill 4.43M / 36; DESIGN.md 7.21M / 45.3. DESIGN.md "required ~92% more tokens," had "~2.7x the variance," and "was more likely to re-create components rather than use the existing system"; it is recommended for "quick prototyping in unfamiliar environments." — [Atlassian: DESIGN.md is here](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)
- `@atlaskit/ads-cli` (16 September 2026): "The CLI and the MCP server call the same handlers, and the skill's reference files are generated from the same source"; 8% faster, 8% fewer tokens, and CLI use 60% higher than MCP. Developer-facing, not a prototyping environment. — [Atlassian: design system context from the terminal](https://www.atlassian.com/blog/ai-at-work/giving-ai-agents-design-system-context-from-the-terminal-what-we-learned-building-a-cli)
- Corpus: hosted ADS MCP at `https://mcp.atlassian.com/v1/ads/public/mcp`, `ads_plan` as the one-shot discovery call, an axe-core analyze-and-fix loop, and per-tool telemetry; outside the React stack, DESIGN.md serves "prototyping, theming, non-React surfaces." — [atlassian.design](https://atlassian.design)

#### Uber (Base)
- AI prototyping (15 April 2026): Lovable, Figma Make, Claude Code and Cursor; 40% of hackathon submissions used prototyping tools; "Two hours of prototyping unblocked four weeks of discussion." The post does not say prototypes were constrained to Base. — [Uber: AI prototyping](https://www.uber.com/blog/ai-prototyping/)
- uSpec (11 March 2026): Cursor agent plus the open-source Figma Console MCP generates six spec types (anatomy, API, properties, color annotation, structure, screen reader); "The agent doesn't guess at property names—it selects from documented APIs." — [Uber: automate design specs](https://www.uber.com/blog/automate-design-specs/)
- Base MCP (12 August 2026): internal remote server exposing 280 doc pages, 700+ tokens with light/dark variants, 3,200+ icons and pointers to platform component repos; 500+ users and 50,000+ tool calls. Failure it targets: "An engineer asking their agent to help migrate legacy code to Base gets hardcoded hex values." And: "Stale design system data fails quietly." — [Uber Design: Base MCP](https://uber.design/base-mcp)

### Inferences
- The field splits into "real package plus guidelines" environments (Figma Make kits, v0 DS 2.0, Lovable, Bolt, UXPin, Builder, Anima) where the model writes free code and adherence is checked later, and in-house MCP/skill/CLI stacks (Atlassian, Uber, Coinbase, Primer, Polaris, SLDS, Carbon) that coerce coding agents. None of them uses a schema-constrained output format, so the "only approved components" guarantee is probabilistic everywhere.
- Atlassian's findings (templates and JSON configuration beat open prompting; DESIGN.md makes agents reimplement components) are the strongest first-party evidence that a constrained output format would help prototyping. An A2UI catalog is essentially structured configuration taken to its end point.
- Every vendor environment has converged on the same four inputs (component package, tokens, prose guidelines, usage examples) and on versioning the design-system context. Lovable, Bolt and Supernova already version it; A2UI versions the catalog. An AG-UI environment has to do both.
- React is the hard requirement in Figma Make kits, Lovable and Storybook manifests. Design systems with web-component or LWC implementations (Carbon, SLDS, Spectrum) are the ones worst served today.

## Key question 3: Recurring requirements, and which are solved

### Takeaway
The component contract, a validation-and-retry loop and design-system versioning each have at least one working implementation. Token binding inside declarative formats, round-tripping generated UI back to Figma as real library instances, and saving generated UI as stories or code in a declarative-format workflow remain open.

### Cited Findings
- Component catalog / contract: A2UI JSON Schema catalogs with negotiation ([A2UI Catalogs](https://a2ui.org/concepts/catalogs/)); json-render `defineCatalog` with Zod ([json-render catalog](https://json-render.dev/docs/catalog)); CopilotKit `createCatalog` ([a2ui-renderer SKILL.md](https://cdn.jsdelivr.net/npm/@copilotkit/a2ui-renderer@1.61.2/skills/a2ui-renderer/SKILL.md)); Tambo `propsSchema` ([docs.tambo.co](https://docs.tambo.co/)); Lovable `design-system.json` ([Lovable](https://docs.lovable.dev/features/design-systems)); Storybook `components.json` manifests (corpus, [Storybook manifests](https://storybook.js.org/docs/ai/manifests)). Existing design-system-side contracts that could feed a catalog: Chakra's MCP uses a Zod enum over the live component list so a nonexistent component "yields a schema validation error" ([chakra mcp tools](https://raw.githubusercontent.com/chakra-ui/chakra-ui/HEAD/apps/mcp/src/tools/index.ts)); Cloudscape publishes per-component JSON API definitions ([Cloudscape alert JSON](https://cloudscape.design/components/alert/index.html.json)); Mantine publishes `mcp/index.json` with full props arrays ([mantine.dev/mcp/index.json](https://mantine.dev/mcp/index.json)).
- Token / theme binding: A2UI has a per-catalog `theme` schema ([A2UI Catalogs](https://a2ui.org/concepts/catalogs/)); CopilotKit passes an A2UI `theme` ([CopilotKit A2UI](https://docs.copilotkit.ai/generative-ui/a2ui)); Figma Make kits include library styles and tokens ([Figma blog](https://www.figma.com/blog/introducing-make-kits-and-make-attachments/)); the v0 legacy flow requires the shadcn CSS-variable standard ([v0 legacy](https://v0.app/docs/design-systems)); Lovable flags raw color literals ([Lovable](https://docs.lovable.dev/features/design-systems)); Supernova keeps only the theme editable in a locked context ([Supernova](https://learn.supernova.io/latest/portal/create/prototyping-contexts-jppeqv9d)); Uber's Base MCP targets hardcoded hex values ([Base MCP](https://uber.design/base-mcp)).
- Validation and repair: A2UI `VALIDATION_FAILED` errors back to the agent ([A2UI spec](https://a2ui.org/specification/v0.9.1-a2ui/)); AG2 schema validation with automatic retry ([AG2](https://docs.ag2.ai/latest/docs/user-guide/ag-ui/a2ui)); OpenUI drops invalid portions and offers Autofix ([OpenUI Lang](https://www.openui.com/docs/openui-lang)); Storybook `run-story-tests` self-healing loop ([Storybook](https://storybook.js.org/docs/ai/mcp/overview)); Primer `lint_css` ([Primer server.ts](https://raw.githubusercontent.com/primer/react/HEAD/packages/mcp/src/server.ts)); Shopify `validate_component_codeblocks` ([dev-mcp](https://unpkg.com/@shopify/dev-mcp@1.14.3/dist/index-6_XnqjXS.js)); SLDS scored validation ([slds-validate](https://raw.githubusercontent.com/forcedotcom/sf-skills/main/skills/design-systems-slds-validate/SKILL.md)); v0's "cannot be verified... should not use it" rule ([v0 DS 2.0](https://v0.app/docs/design-systems-2)).
- Human-in-the-loop: AG-UI documents interrupts and interrupt/resume patterns ([AG-UI llms.txt index](https://docs.ag-ui.com/llms.txt)); CopilotKit v2 has `useHumanInTheLoop` and `useInterrupt` ([CopilotKit reference](https://docs.copilotkit.ai/reference)); the AG-UI draft validates user submissions against an output schema ([AG-UI draft](https://docs.ag-ui.com/drafts/generative-ui.md)). A corpus-listed build report found "the fix was a human gate rather than a better prompt" ([Further reading](https://state-of-ai-in-design-systems.netlify.app/reading)).
- Round-tripping to Figma: Figma Make "Copy design" gives static layers "not automatically tied to your design system" ([Figma Help](https://help.figma.com/hc/en-us/articles/35060759685015-Copy-a-Figma-Make-preview-as-design-layers)); Figma MCP has `generate_figma_design` for live UI to layers (corpus, [Figma MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)); UXPin Merge puts code components in the design tool ([UXPin Forge](https://www.uxpin.com/forge)); Anima goes Figma to code only ([Anima](https://animaapp.com/blog/design-systems/vibe-code-with-your-figma-design-system/)).
- Saving outputs as code / stories: json-render mentions export to standalone React ([json-render.dev](https://json-render.dev/)); UXPin exports JSX ([UXPin Forge](https://www.uxpin.com/forge)); Builder opens branches and PRs ([Builder.io](https://www.builder.io/c/docs/fusion-design-system-intelligence)); Storybook's `dev` toolset has `get-storybook-story-instructions` for agent-written stories (corpus, [Storybook](https://storybook.js.org/docs/ai/mcp/overview)); CopilotKit's VS Code extension stores A2UI fixtures as named JSON/TS scenarios ([CopilotKit VS Code](https://docs.copilotkit.ai/angular/vs-code-extension)).
- Catalog versioning: A2UI's additive/deprecate/versioned-URI rules ([A2UI Catalogs](https://a2ui.org/concepts/catalogs/)); Lovable versioned releases with an update prompt ([Lovable](https://docs.lovable.dev/features/design-systems)); Bolt sync and version history ([Bolt](https://support.bolt.new/building/design-system/introduction)); Supernova context versions apply only to new prototypes ([Supernova](https://learn.supernova.io/latest/portal/create/prototyping-contexts-jppeqv9d)); Primer and Coinbase version their MCP servers in lockstep with the component packages (corpus, [Primer](https://primer.style/product/getting-started/foundations/mcp); [cds.coinbase.com](https://cds.coinbase.com)).

| Requirement | Solved somewhere? | Best existing example | Still open |
| --- | --- | --- | --- |
| Component catalog / contract | Yes | A2UI catalog + `supportedCatalogIds` | Generating the catalog from the design system's source (types, Storybook manifests) automatically |
| Token / theme binding | Partly | Lovable raw-color detection; Supernova locked contexts | Declarative formats have a theme schema but no token model |
| Validation and repair | Yes | A2UI `VALIDATION_FAILED`; AG2 retry; Storybook test loop | Design-rule validation (spacing, a11y) inside declarative formats |
| Human-in-the-loop review | Yes, at runtime | AG-UI interrupts; CopilotKit `useHumanInTheLoop` | Design review of generated surfaces (diff, approve, annotate) |
| Round-trip to Figma | No | Figma "Copy design" (static, unlinked) | Emitting real library instances from generated UI |
| Save as code / stories | Partly | UXPin JSX; json-render export; CopilotKit fixtures | Turning an A2UI surface into a Storybook story or PR |
| Catalog versioning | Yes | A2UI rules; Lovable/Bolt versions | Tying catalog versions to package semver and migrating saved prototypes |

### Inferences
- An AG-UI prototyping environment can take the contract, validation loop, HITL and versioning mostly off the shelf (A2UI catalog, `VALIDATION_FAILED`, AG-UI interrupts, A2UI versioning rules). The differentiators would be (1) generating the A2UI catalog from the design system's existing machine-readable surfaces (Storybook manifests, Cloudscape-style JSON, Mantine index, Code Connect), (2) binding catalog `theme` to the system's real tokens, (3) saving a surface plus its data model as a story or fixture, and (4) round-tripping to Figma through Code Connect mappings instead of static layers.
- Because A2UI surfaces are data, not code, "save as story" and "diff between prototype versions" are cheaper to build than in code-generating tools, where the output is arbitrary React.

### Gaps
- No source reported measured hallucination rates for declarative catalog formats versus code generation on the same design system; the Atlassian, Coinbase and Vercel numbers all concern code generation.
- No tool was found that turns an A2UI or json-render surface into Figma library instances or a Storybook story.

## Key question 4: Writing that connects AG-UI, CopilotKit or A2UI to design systems

### Takeaway
The connection is made by the spec authors, not by design system teams: A2UI's docs and v0.9 post say catalogs should mirror your design system, CopilotKit's `createCatalog` binds catalog definitions to your own React components, and one third-party Angular post shows a custom catalog traveling as an AG-UI context entry. No first-party post from a named design system team connecting AG-UI, CopilotKit or A2UI to its system was found, and the State of AI in Design Systems corpus (21 systems, 6 platforms, July 2026) has zero records mentioning A2UI, AG-UI, CopilotKit, json-render or "generative UI."

- The gap is real and specific: spec authors say "mirror your design system," design system teams have built MCP servers, skills and CLIs for coding agents, and nobody has published the bridge (a design system shipping an A2UI catalog, or a prototyping environment built on AG-UI for a named system). An AG-UI prototyping environment for a design system would be the first public example found.
