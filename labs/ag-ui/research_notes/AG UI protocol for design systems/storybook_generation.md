# Generating UI inside Storybook 10 with AI agents, with a view to AG-UI

Research date: 2026-09-30. Target: `storybook@10.6.1` (npm `latest`, published 2026-09-29). Source code was read at git tag `v10.6.1` of `storybookjs/storybook`. Where a claim is marked "local reproduction", it was run on 2026-09-30 in a throwaway React + Vite project against the published 10.6.1 packages; the cited URL is the source file or doc page that explains the behavior.

## 1. Storybook's AI-facing surfaces in 10.x: addon-mcp, manifests, "Storybook with AI" docs

### Takeaway
Storybook 10.6 ships an official, preview-status AI stack: `@storybook/addon-mcp` mounts an MCP server inside `storybook dev` at `/mcp` (path configurable), backed by JSON manifests at `/manifests/components.json` and `/manifests/docs.json`. The MCP tool names were renamed between the July 2026 snapshot and 10.6 (`list-all-documentation` → `docs-list`, and so on). There is no MCP tool that writes a story; the agent writes files itself after calling `get-storybook-story-instructions`. The components manifest is off by default and must be enabled with `features.componentsManifest: true`.

### Inferences
- For an AG-UI prototype, the manifest is the design-system contract to feed the agent. `components.json` already carries import lines, prop types with descriptions, and real usage snippets. An AG-UI backend can read it over HTTP from the same dev server (`/manifests/components.json`) without MCP at all, or proxy `docs-list` / `docs-show` through `@storybook/mcp` if it wants the same agent-tuned markdown.
- The AG-UI prototype should not depend on MCP tool names being stable. They changed within a single minor-version span (10.3 → 10.6), and the docs repeat that the API "may change".
- The addon-mcp preset is a working reference for hosting a second protocol endpoint (an AG-UI `/agui` route) on the same port: it uses exactly the `experimental_devServer` hook described in section 3.

### Gaps
- I did not find a public statement of the exact release in which the tool renames (`docs-list` etc.) and the move into the monorepo landed. The monorepo `CHANGELOG.md` for addon-mcp stops at 0.7.0, and I did not fetch the 10.4/10.5/10.6 release blog posts.
- No doc lists every `components.json` field as a schema. The field list above combines the docs example with one local build, so fields for subcomponents, errors or the v1 ref format were not observed.

## 2. Programmatic story creation: save from controls, new story file, CSF Factories, writing a story to disk during `storybook dev`

### Takeaway
Storybook has had built-in, server-side story writing since 8.1: the Controls panel's "save as new story" and the sidebar "+" (React only) use request/response channel events (`saveStoryRequest` / `saveStoryResponse`, `createNewStoryfileRequest` / `createNewStoryfileResponse`) handled in Node by `experimental_serverChannel`. None of it is documented as a public API. It works over the dev server's WebSocket, and I drove `saveStoryRequest` from a plain Node WebSocket client to append a new export to a CSF file, including a nested JSON "UI spec" arg. For anything beyond "clone a story with new args", an addon should register its own `experimental_serverChannel` listener and write the file itself with `storybook/internal/csf-tools`.

### Cited Findings

**The UI feature (and its 8.x origin)**
- Storybook 8.1 (May 23, 2024): "you can now create and edit stories from Storybook's UI and React projects can add stories for new components." — [Storybook 8.1 blog](https://storybook.js.org/blog/storybook-8-1/)
- 10.6 docs: "Open the Controls panel for a story and adjust the value of a control. Then save those changes as a new story." For React, "you can click the ➕ button in the sidebar to search for your component and have a basic story created for you." Disable with `parameters.controls.disableSaveFromUI: true`. Not supported with Svelte CSF. — [Controls: Creating and editing stories from controls](https://github.com/storybookjs/storybook/blob/v10.6.1/docs/essentials/controls.mdx); [What's a story](https://github.com/storybookjs/storybook/blob/v10.6.1/docs/get-started/whats-a-story.mdx)

**Channel events (verbatim names and payloads)**
- Event constants: `SAVE_STORY_REQUEST = 'saveStoryRequest'`, `SAVE_STORY_RESPONSE = 'saveStoryResponse'`, `CREATE_NEW_STORYFILE_REQUEST = 'createNewStoryfileRequest'`, `CREATE_NEW_STORYFILE_RESPONSE = 'createNewStoryfileResponse'`, `FILE_COMPONENT_SEARCH_REQUEST = 'fileComponentSearchRequest'`, `FILE_COMPONENT_SEARCH_RESPONSE`, `ARGTYPES_INFO_REQUEST = 'argtypesInfoRequest'`, `ARGTYPES_INFO_RESPONSE`, plus `STORY_RENDERED = 'storyRendered'`, `UPDATE_STORY_ARGS = 'updateStoryArgs'`, `STORY_ARGS_UPDATED = 'storyArgsUpdated'`, `FORCE_REMOUNT = 'forceRemount'`. — [core-events/index.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-events/index.ts)
- Envelope types: `RequestData<P> = { id: string; payload: P }`; `ResponseData<P, E> = { id, success: true, error: null, payload } | { id, success: false, error: string, payload?: E }`. — [request-response.ts types](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-events/data/request-response.ts)
- `SaveStoryRequestPayload { args: string | undefined; csfId: string; importPath: string; name?: string }` and `SaveStoryResponsePayload { csfId; newStoryId?; newStoryName?; newStoryExportName?; sourceFileContent?; sourceFileName?; sourceStoryName?; sourceStoryExportName? }`. — [save-story.ts payload types](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-events/data/save-story.ts)
- `CreateNewStoryRequestPayload { componentFilePath; componentExportName; componentIsDefaultExport; componentExportCount }` returns `{ storyId; storyFilePath; exportedStoryName }` or the error `{ type: 'STORY_FILE_EXISTS'; kind }`. — [create-new-story.ts payload types](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-events/data/create-new-story.ts); [create-new-story-channel.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/server-channel/create-new-story-channel.ts)

**Server implementation**
- The core preset's `experimental_serverChannel` wires `initializeSaveStory`, `initFileSearchChannel`, `initCreateNewStoryChannel`, `initGhostStoriesChannel`, `initOpenInEditorChannel` and others onto the server channel. `build-dev.ts` calls `presets.apply('experimental_serverChannel', channel)`. — [common-preset.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/presets/common-preset.ts); [build-dev.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/build-dev.ts)
- `initializeSaveStory` does the following: reads `join(process.cwd(), importPath)` with `readCsf`; finds the source story by `csfId`; throws "Story already exists." if `name` collides; parses `args` with `JSON.parse` (sentinel `'__sb_empty_function_arg__'` becomes `() => {}`); then either duplicates the story under the new export `name` or updates it in place. It formats with `formatFileContent`, writes the file, waits up to 3000 ms for `STORY_RENDERED` (HMR), and emits `SAVE_STORY_RESPONSE`. — [save-story.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/save-story/save-story.ts)
- CSF support: CSF 3 object stories, and CSF Next stories detected as a call to a `.story` member (`meta.story(...)`), are handled. CSF 2 function stories throw "Updating a CSF2 story is not supported" / "Creating a new story based on a CSF2 story is not supported". — [update-args-in-csf-file.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/save-story/update-args-in-csf-file.ts); [duplicate-story-with-new-name.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/save-story/duplicate-story-with-new-name.ts)
- The new-story-file generator switches to a CSF Factory template when the project's preview is a CSF factory preview (`isCsfFactoryPreview`, `getCsfFactoryTemplateForNewStoryFile`). — [get-new-story-file.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/get-new-story-file.ts)
- Manager side: the Controls addon calls `experimental_requestResponse(channel, SAVE_STORY_REQUEST, SAVE_STORY_RESPONSE, { args: stringifyArgs(...), csfId: data.id, importPath: data.importPath, name })`, using `api.getCurrentStoryData()`. On save-in-place it sends only args that differ from `initialArgs`. — [controls/manager.tsx](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/controls/manager.tsx)
- `experimental_requestResponse(channel, requestEvent, responseEvent, payload, timeout = 5000)` is exported from `storybook/manager-api`; it generates a random `id` and resolves on the matching response. — [request-response.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/manager-api/lib/request-response.ts)
- CSF read/write helpers exist in `storybook/internal/csf-tools`: `loadCsf`, `formatCsf`, `printCsf`, `readCsf`, `writeCsf`. — [CsfFile.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/csf-tools/CsfFile.ts)
- Local reproduction: connecting with the `ws` package to `ws://localhost:<port>/storybook-server-channel?token=<wsToken>` (the token is printed into `iframe.html` as `CHANNEL_OPTIONS = {"wsToken":"..."}`) and sending `{"type":"saveStoryRequest","args":[{"id":"req1","payload":{"csfId":"components-button--primary","importPath":"./src/components/Button.stories.tsx","name":"GeneratedFromAgent","args":"{...}"}}],"from":"probe"}` produced `saveStoryResponse` with `success: true`, `newStoryId: "components-button--generated-from-agent"`, and appended `export const GeneratedFromAgent: Story = { args: {...} };` to the file. `/index.json` listed the new story within about 2 s. A second save with a nested `spec` arg (`{ root, elements: { r: { type: 'Stack', props, children } ... } }`) serialized correctly as an object literal, though with blank lines between properties when Prettier was not installed. — explained by [get-server-channel.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/get-server-channel.ts) (path check, `token` query param, `telejson` parse) and [save-story.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/save-story/save-story.ts)
- The server channel's WebSocket rejects browser `Origin`s that fail host validation (403) and any request without a valid `token` (401). "an absent one means a non-browser client, which the token alone authenticates." — [get-server-channel.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/utils/get-server-channel.ts)
- `storybook` declares `prettier: ^2 || ^3` as a peer dependency. — [npm registry: storybook](https://registry.npmjs.org/storybook)

**CSF Factories / CSF Next (10.x)**
- CSF Next is a "preview" feature. The chain is `definePreview` → `preview.meta` → `meta.story`, plus `defineMain`, `preview.type<...>().meta(...)` and `<Story>.extend(...)`. Imports: `import { defineMain } from '@storybook/your-framework/node'` and `import { definePreview } from '@storybook/your-framework'`. Official addons are imported as default exports (`import addonA11y from '@storybook/addon-a11y'`). — [CSF Next API](https://storybook.js.org/docs/api/csf/csf-next.md)
- A test syntax on top of CSF Next is still experimental behind the `experimentalTestSyntax` feature flag. — [CSF Next API](https://storybook.js.org/docs/api/csf/csf-next.md)

### Inferences
- "Save the generated UI as a story" maps cleanly onto the existing save flow if the generated UI is represented as JSON args on a host story. For example, a `GeneratedCanvas` story whose single `spec` arg is a json-render / A2UI-style tree that a renderer maps onto design-system components. `saveStoryRequest` with `name` then writes `export const MyScreen = { args: { spec: {...} } }`, and the story renders from data, with no generated JSX to lint. Three limits: args must be JSON-serializable (functions collapse to no-ops), the source story must be CSF 3 or CSF Next, and the channel exists only in dev.
- If the goal is a JSX story (what Story UI and the MCP workflow produce), the save-story event is the wrong tool. A custom `experimental_serverChannel` handler (section 3) should generate CSF text, then either write it with `writeFile` or build it with `loadCsf`/`printCsf`. HMR and the story indexer pick up the new file, as with any story file.
- `disableSaveFromUI` appears to gate only the Controls UI. The server handler in `save-story.ts` does not check it. That is my reading of the source, not documented behavior.

### Gaps
- None of these events or `experimental_requestResponse` appear in the public addon API docs. They are internal (`storybook/internal/core-events`) and could change without a major version.
- I found no official "save story" API for CSF Next-only projects beyond the `.story` call detection in source. I did not test save-story against a CSF Next file locally.

## 3. Addon API for the prototype: panel, channel, args, decorators/loaders, and server hooks to host an AG-UI endpoint

### Takeaway
A Storybook 10 addon can hold everything the prototype needs. A manager panel (`addons.register`, `types.PANEL`, `useChannel`, `useArgs`) can host the chat and event log. A preview-side renderer can live inside a story's `render` (or a decorator). A preset can add `experimental_devServer` (mount a POST + SSE route such as `/agui` on the Storybook port) and `experimental_serverChannel` (Node listeners that write files). Both server hooks are undocumented, but core and `@storybook/addon-mcp` use them, and I verified both locally. Storybook 10 is ESM-only; Node 20.19+ or 22.12+ per the migration guide.

### Cited Findings

**Manager-side panel**

### Inferences
- The simplest architecture on one port uses a local preset. It exports `experimental_devServer` to mount `POST /agui`: an AG-UI agent endpoint that reads `/manifests/components.json` for its tool and catalog prompt and streams AG-UI events over SSE. The same preset exports `experimental_serverChannel` to handle a custom `agui/save-story` event that writes a CSF file. A manager panel uses `@ag-ui/client`'s `HttpAgent` against `/agui` and forwards render instructions to the preview with `useChannel` `emit`. A host story's `render` holds a React component that subscribes with preview `useChannel` (or reads `spec` from args via `updateArgs`) and maps specs to design-system components. Loaders are the wrong fit because they resolve once before render.
- Alternatively the preview can call `/agui` directly. The manager and preview are served from the same origin in dev, so no CORS work is needed, but the panel is the better place for chat state that should survive story switches.
- Everything in that design is dev-only. `storybook build` output has no `/agui`, no `/mcp`, no server channel and no save-story. A static smoke test can check the renderer against saved specs but not the live stream.
- Because the `open-service` toolsets carry a `'sdk'` transport and the MCP adapter is just a wrapper, an AG-UI backend running in the same Node process could in principle call `getToolset('docs')` directly instead of speaking MCP. The README frames it as internal, so treat that as unsupported.

### Gaps
- No official doc confirms `experimental_devServer` or `experimental_serverChannel` as supported extension points. Their names carry `experimental_`, and they are absent from the docs, so they could change in 11.x (`11.0.0-alpha.1` is already on `next`).
- I did not test whether `experimental_devServer` handlers run before or after Vite's own middleware for paths that collide. I used a non-colliding `/agui` path.
- I did not verify SSE buffering behavior behind the dev server's `@polka/compression` middleware under a long-running stream. My test stream was two events. Flush behavior on long streams should be tested early in the prototype.

## 4. Existing projects that generate UI in Storybook with AI, and any AG-UI / CopilotKit / A2UI / json-render use

### Takeaway
The official path is Storybook MCP: agents write JSX story files themselves, guided by `get-storybook-story-instructions`, and validate with `test-run`. The most complete third-party generator is Southleft's Story UI, which writes `.stories.tsx` files from its own Node server with a custom SSE event schema, not AG-UI. I found no project that drives Storybook with AG-UI, and no Storybook integration from CopilotKit beyond its own component workshop. A few small repos render json-render or A2UI specs inside stories, which is the closest prior art to "spec-driven generated UI saved as a story".

## 5. Testing hooks to validate an agent-generated story automatically

### Takeaway
A generated story can be checked with the same tools Storybook recommends for agents: `@storybook/addon-vitest` (every story becomes a Vitest browser test via Playwright), `@storybook/addon-a11y` with `parameters.a11y.test: 'error'` to fail on axe violations, `play` functions for interaction tests, and Chromatic's visual tests. The MCP `test-run` tool wraps the Vitest run for agents but is only registered when addon-vitest is installed.

### Cited Findings
- `test-run` "Runs tests for specific stories and returns results, including any accessibility issues (if configured). Also instructs the agent to interpret the results and resolve any issues found." The docs call this a "self-healing loop". — [MCP server overview](https://storybook.js.org/docs/ai/mcp/overview.md)
- Vitest addon: `npx storybook add @storybook/addon-vitest`. The config uses the `storybookTest({ configDir, storybookScript })` plugin in a Vitest project named `storybook` with `browser: { enabled: true, provider: playwright({}), headless: true, instances: [{ browser: 'chromium' }] }` and `setupFiles: ['./.storybook/vitest.setup.ts']` (Vitest 4 form). Run headless with `vitest --project=storybook`. — [Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon.md)
- `@storybook/addon-vitest@10.6.1` peers: `vitest ^3 || ^4 || ^5`, `@vitest/browser`, `@vitest/runner`, `@vitest/browser-playwright ^4 || ^5`. — [npm registry: @storybook/addon-vitest](https://registry.npmjs.org/@storybook/addon-vitest)
- Accessibility: `parameters.a11y.test` accepts `'off'`, `'todo'` ("violations return a warning") and `'error'` ("violations return a failing test in the Storybook UI and CLI/CI"). `parameters.a11y.context`, `config` and `options` pass through to axe. `@storybook/addon-a11y@10.6.1` depends on `axe-core`. — [Accessibility tests](https://storybook.js.org/docs/writing-tests/accessibility-testing.md); [npm registry: @storybook/addon-a11y](https://registry.npmjs.org/@storybook/addon-a11y)
- Interaction tests: `play: async ({ canvas, userEvent }) => { await userEvent.type(canvas.getByTestId('email'), ...); await userEvent.click(canvas.getByRole('button')); await expect(canvas.getByText(...)) ... }`. — [Interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing.md)
- Visual tests: `npx storybook@latest add @chromatic-com/storybook` adds a Visual Tests panel; "every story is automatically turned into a test". — [Visual tests](https://storybook.js.org/docs/writing-tests/visual-testing.md)
- Agentic setup's verify step: "run Vitest against every new story to confirm it renders, and run the type checker", and new stories are tagged `ai-generated` "for your review". — [Agentic setup](https://storybook.js.org/docs/ai/setup.md)
- Core also runs "ghost stories" over the server channel (`GHOST_STORIES_REQUEST` / `GHOST_STORIES_RESPONSE`), which gathers component candidates and calls a `runStoryTests` utility. This is internal. — [common-preset.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/presets/common-preset.ts); [ghost-stories-channel.ts](https://github.com/storybookjs/storybook/blob/v10.6.1/code/core/src/core-server/server-channel/ghost-stories-channel.ts)
- The docs' guidance on story design for agents: one concept per story, and JSDoc `@summary` feeding the manifest. — [Best practices](https://storybook.js.org/docs/ai/best-practices.md)

### Inferences
- A practical post-generation gate for the prototype runs in four steps. (1) After `saveStoryResponse`, run `vitest --project=storybook` filtered to the new story file, which covers render success, play functions and axe when `a11y.test: 'error'` is set in `preview.ts`. (2) Tag generated stories (for example `tags: ['ai-generated']`, as agentic setup does) so reviewers and CI can find them. (3) Optionally run Chromatic for visual baselines. (4) If an MCP-capable agent is in the loop, let it call `test-run` instead.
- Validating a spec before rendering (props against `reactDocgen` types in `components.json`) is something the prototype has to build. Story UI does it against TypeScript and Storybook MCP does it by instruction, but no official validator exists for a JSON spec.

### Gaps
- I did not run addon-vitest locally, so the exact CLI filter for a single story file and the runtime cost per story are unverified.
- The `test-run` input schema was not observed (the tool was absent in my local run without addon-vitest).

### Inferences
- For the prototype's CI smoke test, `storybook build` proves the renderer and saved stories compile and that manifests are generated. A second check, `vitest --project=storybook` (which starts its own Storybook via `storybookScript` in the documented config), proves stories render in a browser. Neither covers the live AG-UI route, which needs `storybook dev` running plus an HTTP probe like the `curl -X POST /agui` used above.
- Add `@storybook/addon-vitest`, `vitest`, `@vitest/browser-playwright` and `playwright` only when the test step is wanted. Add `@storybook/addon-a11y` to get axe results into both Vitest and `test-run`.
- Initialize git in the prototype repo. `stories-changed`, `review-create` and change detection depend on it (the dev server warns without it).
